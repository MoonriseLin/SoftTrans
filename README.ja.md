# Softdrop

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md) · **日本語**

スマホからパソコンへ、ノートパソコンからタブレットへ。Web ページだけで、手元のデバイス間でファイルやテキストを送れます。同じ Wi-Fi につながっていれば、データは LAN 内でデバイス同士が直接やり取りします。通信はすべてエンドツーエンドで暗号化されます。サーバーはデバイス同士を引き合わせるだけで、送った内容を見ることはありません。

**試してみる：** 2 台のデバイスで **[https://mio.pantsu.uk](https://mio.pantsu.uk)** を開いてください。

インストールは不要です。iPhone や Android ではページをホーム画面に追加して、アプリのように使えます（PWA）。表示言語は英語・简体中文・繁體中文・日本語に対応しています。最初はブラウザの言語に合わせて表示され、画面上部で選んだ言語は記憶されます。

---

## 使い方

1. 2 台のデバイスでページを開きます。同じ Wi-Fi なら、1〜2 秒でお互いのレーダーに表示されます。
2. 送り先のデバイスをタップします。
3. テキストを入力するか、**貼り付け** をタップしてクリップボードの内容（テキストや画像）を入れるか、ファイルをドロップまたは選択して、**送信** をタップします。
4. 相手のデバイスは確認なしで、すぐに受信を始めます。両方の画面に、受信済みのサイズと全体のサイズ（例：`50.5 MB / 200.3 MB`）と速度が表示されます。
5. 転送ごとに、どの経路で届いたかが表示されます。
   - **直接 · 同じ Wi-Fi**：LAN 内でデバイス同士が直接やり取りします。最も速く、サーバーの負担もありません。
   - **直接**：NAT 越えを使い、インターネット越しにデバイス同士が直接やり取りします。
   - **リレー経由**：サーバーのリレーを通ります。直接つながらないときだけ使われ、この場合もエンドツーエンドで暗号化されています。

**別のネットワークにあるデバイス**（例：モバイル通信のスマホと自宅のパソコン）は、一度だけペアリングします。

1. 片方のデバイスで **コードを表示** をタップすると、4 桁のコードが出ます（5 分間有効）。
2. もう片方のデバイスでそのコードを入力し、**ペアリング** をタップします。すぐにペアリングが完了します。

これ以降は、2 台ともオンラインであれば、どのネットワークにいてもお互いを見つけられます。

## デバイス間のしくみ

```
 スマホ（ブラウザ / PWA）                                 パソコン（ブラウザ）
        │                                                        │
        │ 1. WebSocket（WSS）：登録、相手探し、署名付きの接続情報の交換 │
        └───────────────────────►  サーバー  ◄────────────────────┘
                          シグナリング · STUN/TURN · ページ配信

        2. WebRTC データチャネル。エンドツーエンドで暗号化（DTLS）：
           a. LAN 内で直接 .......................... 最優先
           b. NAT 越えで直接（STUN）................. 別のネットワーク
           c. TURN リレー経由 ....................... 最後の手段
```

### 1. デバイスごとの ID

初めて開いたとき、ブラウザは WebCrypto で **ECDSA P-256 の鍵ペア** を作ります。秘密鍵は取り出せない形でブラウザの IndexedDB に保存されます。**デバイス ID は公開鍵の SHA-256 ハッシュ** です。ID が鍵から決まるため、ほかのデバイスの ID をなりすますことはできません。各デバイスには「Quiet Fox」のようなランダムな名前も付きます。この名前は変更できます。

アカウントはありません。ID はデバイス（ブラウザ）ごとです。

### 2. 登録と近くのデバイスの発見

ページはサーバーと WebSocket でつながります。サーバーがランダムなチャレンジを送り、デバイスは秘密鍵で署名して返します。署名が正しく、ID と鍵が一致したときだけ登録されます。

サーバーは、自分から見えた **グローバル IP アドレス** でデバイスをグループ分けします（IPv6 は /64 プレフィックス単位）。同じ家庭用ルーターの内側にあるデバイスは同じグローバル IP を使うので、設定なしでお互いが **近くのデバイス** として表示されます。大きな共有 NAT（会社、キャンパス、携帯キャリア）の内側では、知らない人と同じグループになることがあります。転送は自動で受け取られるので、同じグループの人なら誰でも送ってこられます。ページには、近くに誰がいるかと、各転送の送り主が常に表示されます。

**ペアリング済みのデバイス** は、どのネットワークにいてもお互いが見えます。サーバーは、*両方* が相手を信頼している場合に限って、2 台をお互いに表示します。この情報はメモリ上にだけ置かれ、ディスクには保存されません。

### 3. 直接つなぐための準備（シグナリング）

ブラウザ同士が直接つながるには、先に接続情報を交換する必要があります。WebRTC の **offer**、**answer**、**ICE 候補**（使えそうなネットワークアドレス）です。サーバーはこれらを中継しますが、改ざんはできません。

- すべてのメッセージは送り手のデバイス鍵で **署名** されていて、受け手は使う前に署名を確認します。
- offer と answer には、その接続の暗号化（DTLS）に使う証明書のフィンガープリントが入っています。フィンガープリントは署名の対象なので、固定（ピン留め）されます。接続後には、実際に使われた証明書がそれと一致するかをもう一度確認します。

そのため、悪意のあるサーバーも、同じ Wi-Fi にいるほかの人も、間に割り込んであなたのデバイスになりすますことはできません。まだペアリングしていないデバイスについては、サーバーが正しい相手を紹介していると信頼することになります。ペアリングすると相手の公開鍵が保存され、以降の接続はその鍵で確認されます。ペアリング自体はサーバーと 4 桁のコードを信頼する仕組みで、確認用の数字を見比べる手順はありません。

### 4. 経路の選び方

WebRTC の ICE は、考えられる経路をすべて同時に試し、つながった中で一番よいものを使います。

| 経路 | 使われる場面 | 表示 |
| --- | --- | --- |
| LAN（host 同士） | 同じ Wi-Fi で、デバイス同士が通信できるとき | 直接 · 同じ Wi-Fi |
| STUN（NAT 越え） | 別のネットワークで、ルーターが NAT 越えを許すとき | 直接 |
| サーバーの TURN リレー | 厳しい NAT、クライアント分離のあるゲスト Wi-Fi、UDP が使えないネットワーク | リレー経由 |

表示は、ブラウザが実際に選んだ接続（`getStats()`）をもとにしているので、本当の状態を表しています。リレー経由のデバイスは、レーダー上で点線の輪でも示されます。リレーは、サーバーが発行する有効期限付きの認証情報で使います。暗号化されたパケットを中継するだけで、ディスクに書き込むことはありません。

### 5. ファイルの送り方

やり取りはすべて、信頼性があり順序が保たれる 1 本の **データチャネル** で行います。

1. 送り手が、転送の名前・サイズ・種類を知らせます。16 KB 以下の短いテキストは、この通知にそのまま入ります。
2. 受け手は自動で受け取り、保存先を用意します。
3. ファイルは **64 KB ずつ**（相手のブラウザが大きなメッセージを受けられない場合は 16 KB ずつ）送られます。送信は背圧（バックプレッシャー）で調整されるので、送り手が速すぎてもメモリがあふれることはありません。受け手が進み具合を返し、両方の画面の進捗リングと速度の表示に使われます。
4. 両方がファイル全体の **SHA-256 ハッシュ** を計算します。一致した場合だけ、受け手はファイルを保存します。
5. 大きなファイルは、ブラウザが対応していればブラウザ専用の保存領域（OPFS）に、そうでなければ Blob として保存されます。そのあと **保存**（スマホでは **共有** も）をタップします。

どちらの側からもキャンセルできます。途中で接続が切れた場合（画面ロックや Wi-Fi の切り替えなど）は一時停止し、再びつながったところで続きから再開します。

### サーバーに見えるもの・見えないもの

| サーバーが知っていること | サーバーが決して見ないもの |
| --- | --- |
| 接続中のデバイスの ID・名前・種類・グローバル IP | 送ったファイルの中身やテキスト |
| オンラインの間、どのデバイス同士がペアリングしているか | ファイル名やサイズ（暗号化されたチャネルの中を通るため） |
| 接続が確立したこと、TURN を使ったときの中継バイト数 | あなたの秘密鍵 |

アカウントも、トラッキングも、アクセス解析もありません。

## 知っておくと便利なこと

- **スマホではページを開いたままにしてください。** iOS や Android はバックグラウンドの Web ページを止めるので、転送も止まります。転送中は、ブラウザが許す範囲で画面がスリープしないようにします。
- **ゲスト Wi-Fi や公衆 Wi-Fi** では、デバイス同士の通信が遮断されていることがよくあります（クライアント分離）。その場合はリレー経由になり、使えますが遅くなります。
- **iPhone で非常に大きなファイル** を扱うと、Safari のメモリ制限にかかることがあります。
- 同じブラウザの 2 つ目のタブで Softdrop を開くと、そのデバイスは新しいタブのほうに移ります。
- アドレスの末尾に `?relay=1` を付けると、リレー経由に固定できます（テスト用）。
- **デバッグログ**：接続と転送の各ステップを記録し、サーバーのログに送ります。ログ画面は非表示で、アドレスの末尾に `?debug=1` を付けると表示されます。`?debug=0` で記録を止められます。サーバー側では `sh deploy/logs.sh` でログを追えます。

## 開発者向け

```
server/      シグナリングサーバー（Node 20 + ws）：在席管理、IP によるグループ分け、ペアリングコード、
             署名付きシグナリングの中継、TURN 認証情報
web/         アプリ本体。ビルド不要：index.html、app.css、js/*.js、Service Worker、manifest、アイコン
  js/identity.js   デバイスの鍵、信頼済みデバイス
  js/signaling.js  WebSocket クライアント
  js/rtc.js        WebRTC 接続、署名の確認、DTLS のピン留め、経路の判定
  js/transfer.js   転送プロトコル（meta/accept/分割/ハッシュ/キャンセル/再開）
  js/sinks.js      受信データの保存先（OPFS または Blob）
  js/i18n.js       英語、简体中文、繁體中文、日本語
e2e/         2 つのブラウザを使うエンドツーエンドテスト（Playwright）
deploy/      nginx サイト、systemd ユニット、coturn 設定、インストールスクリプト
prototype/   最初のフロントエンド試作（見た目の参考）
docs/        デザイン方針、プロトコル（「As built」を参照）、デプロイメモ
```

**ローカルで動かす**

```sh
cd server && npm install && npm start    # http://127.0.0.1:8480
npm test                                 # ユニットテスト
```

同じパソコンで 2 つのブラウザプロファイル（通常ウィンドウとプライベートウィンドウなど）を使うと、お互いが近くのデバイスとして表示されます。`TURN_HOST` と `TURN_SECRET` を設定しない場合は、直接の経路だけが使えます。

**エンドツーエンドテスト**

```sh
cd e2e && npm install && npx playwright-core install chromium-headless-shell
node run.mjs                                       # ローカルのサーバーに対して
BASE=https://mio.pantsu.uk node run.mjs       # 本番環境に対して
QUERY='?relay=1' WANT_ROUTE=relay WANT_LABEL='Via relay' BASE=https://mio.pantsu.uk node run.mjs
```

**デプロイ（VPS 上で）：** `sh deploy/install.sh`。nginx・coturn・証明書については [docs/deploy-notes.md](docs/deploy-notes.md)、メッセージ形式は [docs/protocol-draft.md](docs/protocol-draft.md)（英語）を参照してください。
